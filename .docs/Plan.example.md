> ## Plan 与 Task 的边界
>
> | 维度 | Plan（计划） | Task（任务） |
> |------|------------|------------|
> | **关注点** | 「做什么」与「为什么」——阶段划分、架构决策、风险识别、依赖关系 | 「怎么做」——原子化的实施步骤，明确到文件、函数、接口 |
> | **粒度** | Phase 级别，一个 Phase 对应一个可交付增量 | 单文件/单功能级别，每个 Task 可独立验证 |
> | **受众** | 开发者 + 决策者，用于对齐方向 | 执行者，用于逐项落实 |
> | **内容** | 背景目标、阶段划分、架构决策、风险、依赖关系 | 编号、状态、描述、Details、验收标准、依赖与优先级 |
> | **生命周期** | 一个 Plan 覆盖整个功能/需求，Phase 完成后归档 | 随 Phase 推进逐步完成，全部 DONE 后随 Plan 归档 |
> | **禁止出现** | 具体文件名、函数签名、代码片段 | 模糊动词（如"优化""完善"）、跨模块大重构（Quick 模式） |
>
> **转换规则**：一个 Plan Phase 可拆解为 N 个 Task；Task 是 Plan 的执行单元，Plan 是 Task 的上层设计。Plan 决定"走到哪"，Task 决定"怎么走"。同一个 Phase 的 Task 之间允许有依赖，但跨 Phase 的 Task 依赖应在 Plan 的风险/依赖中体现。

# Plan：用户认证模块

**状态**：DONE  
**日期**：2026-06-25  
**版本**：v1.0  
**回归测试结论**：全部集成测试通过，覆盖率 85%，无回归问题。

---

## 1. 背景与目标

当前系统缺乏用户认证机制，所有接口对外开放。本次计划引入 JWT 登录与 RBAC 权限控制，实现以下目标：

- 用户可通过用户名/密码登录获取访问令牌
- 基于角色的权限控制（管理员、编辑者、查看者）
- 令牌有效期 2 小时，支持刷新

## 2. 阶段划分

### Phase 1：数据库设计与用户表迁移

| 项目 | 内容 |
|------|------|
| **输入** | 现有数据库 schema |
| **输出** | `users`、`roles`、`permissions` 三张表，含索引与初始数据 |
| **验收标准** | 迁移脚本可重复执行，回滚脚本就绪，初始角色数据完整 |

### Phase 2：登录 / 注册 API 实现

| 项目 | 内容 |
|------|------|
| **输入** | Phase 1 的数据库表 |
| **输出** | `POST /auth/login`、`POST /auth/register` 两个端点 |
| **验收标准** | 登录成功返回 JWT，注册校验邮箱唯一性，密码 bcrypt 哈希存储，错误响应对照 HTTP 语义 |

### Phase 3：JWT 中间件与 RBAC 鉴权

| 项目 | 内容 |
|------|------|
| **输入** | Phase 2 的令牌签发逻辑 |
| **输出** | `AuthMiddleware` + `RequireRole` 装饰器 |
| **验收标准** | 未认证请求返回 401，无权限请求返回 403，中间件对公开路由放行 |

### Phase 4：接口测试与文档更新

| 项目 | 内容 |
|------|------|
| **输入** | 前三阶段的全部代码 |
| **输出** | 集成测试用例 + 更新后的 API 文档 |
| **验收标准** | 测试覆盖率 ≥ 80%，文档与实现一致，边界场景覆盖（过期令牌、篡改令牌、并发登录） |

## 3. 架构决策

| 决策项 | 选择 | 理由 | 替代方案（为何不选） |
|--------|------|------|----------------------|
| 数据库 | PostgreSQL | 事务支持强、JSON 字段灵活 | MySQL（RBAC 多对多查询性能不足） |
| 会话存储 | Redis | 高性能、原生 TTL、支持集群 | 内存存储（不支持多实例部署） |
| 密码哈希 | bcrypt, cost=12 | 行业标准、抗暴力破解、库成熟 | argon2（依赖复杂，当前语言绑定不稳定） |
| 令牌格式 | JWT (RS256) | 非对称签名、无状态验证、支持多服务 | HS256（密钥分发困难，扩展性差） |
| 权限模型 | RBAC | 需求明确、实现简单、团队熟悉 | ABAC（当前需求下过度设计） |

## 4. 风险清单

| 风险 | 等级 | 缓解措施 |
|------|------|----------|
| JWT 密钥轮转机制未确定，影响后续无感刷新 | 🟡 中 | 预留密钥版本字段，Phase 1 数据库设计加入 `kid` 字段 |
| 现有接口无认证，上线后大面积 401 | 🔴 高 | 分阶段灰度发布，先加白名单，逐步收紧；提前通知调用方 |
| Redis 单点故障导致全部会话失效 | 🟡 中 | Redis Sentinel 备选，Phase 3 预留数据库 fallback 接口 |
| 密码重置流程未设计，用户锁定时无自助途径 | 🟢 低 | 本次不实现，Phase 4 文档中标注为已知限制 |

## 5. Phase 依赖关系

```
Phase 1 ──→ Phase 2 ──→ Phase 3 ──→ Phase 4
```

Phase 1 至 3 严格串行；Phase 4 待接口契约就绪后展开。

## 6. Subagent 协同规划

对照三维效益模型（任务复杂度、上下文关联度、经济与时间效益）评估本阶段委托需求：

| 阶段 | 上下文依赖 | 并行收益 | 执行主体 | 决策理由 |
|------|-----------|---------|----------|----------|
| Phase 1：数据库设计 | 强（涉及全局 schema 与初始实体） | 无（主干基石） | 主线 | 避免隔离会话因上下文缺失遗漏主键约束 |
| Phase 2：登录/注册实现 | 强（依赖 Phase 1 结构及错误模型） | 无（核心业务链路） | 主线 | 涉及认证状态流转，主线推演直接修改更高效 |
| Phase 3：中间件鉴权 | 强（涉及核心上下文注入与守卫） | 无（依赖 Phase 2 接口） | 主线 | 差分小且调用密集，主线处理无冷加载损耗 |
| Phase 4：测试与文档 | 低（前序接口已定型，只读参照） | 高（测试与文档可并行编写） | Subagent: executor | 边界自包含且耗时较长，委托可节约端到端时延 |

> **协同结论**：Phase 1-3 强依赖领域上下文且呈严格串行，由主线高效推进；Phase 4 具有高独立性，接口契约稳定后委托 Subagent: executor 并行编写集成测试与文档。
