## 1. 背景与目标

多模态 AI Agent 处理长视频时受上下文长度限制，直接投喂会占用大量上下文并诱发幻觉。把长视频按每秒随机抽帧重渲染为低分辨率短视频，同时将音频分离为独立压缩文件，两条通道分别投喂 AI，可在压缩上下文的同时保留视觉与听觉信息，互为补充。

本次交付一个 Windows 桌面工具，实现以下目标：

- 读取 mp4（及 ffmpeg 可解容器）元数据；
- 按每秒随机保留 m 帧的方式重渲染为低分辨率短视频：默认 720p，输出帧率等于源帧率 a，输出时长约为 `n × m / a` 分钟（n 为源时长）；
- 分离音频为独立压缩文件（默认 AAC / .m4a，保持原始时长）；
- 参数可视化配置（每秒保留帧数、输出分辨率、音频格式、编码器 / GPU 等）；
- 优先调用 GPU 硬件编解码，自动探测、失败回退 CPU。

**抽帧与重渲染模型**：源视频 `n` 分钟、`a` fps，共 `60·n·a` 帧。按概率 `p = m / a` 随机保留帧，得到约 `60·n·m` 帧；将其重打包为 `a` fps 连续帧，输出时长 `60·n·m / a` 秒 = `n·m/a` 分钟。「每秒保留帧数 m」等价于需求中的「每分钟抽帧数 = 60m」。

## 3. 架构决策

| 决策项 | 选择 | 理由 | 替代方案（为何不选） |
|--------|------|------|----------------------|
| 处理引擎 | ffmpeg / ffprobe 子进程 | 成熟稳定、原生支持全格式与 GPU 编解码、无 cgo | goav / astiav（cgo 绑定，Windows 交叉编译与分发复杂） |
| 桌面外壳 | Wails v2 | Go 后端 + WebView2，Win11 自带运行时，可产出单 exe | Fyne（非 Fluent，观感差距大）；walk（Win32 控件陈旧）；Electron（非 Go，体积大） |
| 前端 | React + Fluent UI React v9 | 官方 Fluent 组件，观感与 Win11 一致，与 `fluentui-docs` MCP 对齐 | 手写 HTML/CSS（一致性靠自律、成本高）；其他组件库（非 Fluent） |
| 抽帧策略 | 每秒随机保留 m 帧（概率 `p = m/a`）→ `setpts` 重打包、输出 `fps = a` | 随机采样避免固定相位造成的运动混叠；单条滤镜链即可表达 | 固定采样 `mod(n,a)<m`（相位固定、易混叠）；导出全帧图片序列（上下文仍大） |
| 音频 | 独立文件、保持原始时长、重编码格式 AAC / MP3 / FLAC（默认 AAC/.m4a） | 与视频分离投喂并保留音频细节；FLAC 满足「最大程度保留细节」 | 与视频混流（违背分离目的）；WAV（相对 FLAC 无增益且体积更大）；时间拉伸对齐（损伤细节） |
| ffmpeg 分发 | 首次启动自动下载 + 校验 + 缓存，支持手动指定路径 | 用户选择；产物体积小、免安装 | 随包内置（产物增大 30–80MB）；依赖系统安装（环境门槛） |
| ffmpeg 来源与校验 | 固定到 BtbN/FFmpeg-Builds 的**日期化 autobuild tag**（如 `autobuild-2026-10-08-13-05`，不可变），资产 `ffmpeg-<ver>-win64-gpl[-<branch>].zip`（静态 GPL，含 nvenc / nvdec / amf / qsv / d3d11va）；以同 release 的 `checksums.sha256` 校验 | tag 不可变 → 可复现（同 URL 同字节）；`checksums.sha256` → 完整性校验，二者职责不同 | `latest` 滚动 tag（内容每日重生成，不可复现）；内置 SHA-256 常量（随上游更新失效） |
| GPU | 硬件解码（探测可用时注入 `-hwaccel`）+ 硬件编码（`-encoders` + 全链路自检），不可用时回退软解 / `libx264` | 用户选择；跨厂商兼容、失败不阻塞 | 仅 CPU（慢）；指定单一厂商（泛用性差） |
| 输出命名与覆盖 | 固定后缀 `<源名>.cat.<ext>` / `<源名>.cat.<aext>` / `<源名>.cat.meta.json`；同名输出直接覆盖 | 命名可预测、结果可机械判定；单一覆盖策略避免歧义 | 加时间戳 / 序号（难判定）；重名拒绝（多一个分支） |

## 4. 风险清单

| 风险 | 等级 | 缓解措施 |
|------|------|----------|
| 开发环境（WSL）未安装 ffmpeg，后端管线无法本机验证 | 🔴 高 | Phase 1 安装 ffmpeg 作为开发依赖；CI 使用预装 ffmpeg 的 runner；管线参数构建以命令断言单测先行 |
| WSL 缺少 Wails v2 运行依赖（WSLg + webkit2gtk 等），`wails dev` 可能无法启动窗口 | 🟡 中 | Phase 1 预装依赖并执行 `wails doctor` 核对；必要时退回「Vite dev 跑前端 + Go 单测跑后端」双轨验证 |
| GPU（NVENC / QSV / AMF）无法在 Linux 开发环境验证 | 🔴 高 | 能力探测与命令构建做单元测试；实测列进 Windows 手动验收清单 |
| 注入 `-hwaccel` 后硬件帧与软件滤镜链（select/setpts/scale）不兼容导致解码失败 | 🟡 中 | 不设置 `-hwaccel_output_format`（默认回传系统内存）；TASK-003 以「硬解 + 滤镜链 + 编码」全链路自检验证，未通过则不注入硬解；列入 Windows 验收 |
| 自动下载源不稳定或缺少校验 | 🟡 中 | 固定不可变 tag + 同 release 的 `checksums.sha256` 校验；失败时提示手动指定 ffmpeg 路径 |
| Windows exe 仅由云端 CI 构建，本机禁止全量构建 | 🟡 中 | 建 Windows runner 工作流；本机仅跑 Go 单测与前端 dev 验证 |
| 随机抽帧的确定性未知（ffmpeg `random()` 是否按输入确定，尚未实测） | 🟢 低 | Phase 2 实测同输入两次运行输出是否一致，据实修正本节描述；如需可控复现改用确定性采样 |
| 输出时长存在偏差（源为 VFR 或非整数帧率） | 🟢 低 | 以 ffprobe 平均帧率为基准；结果 JSON 记录实测值 |

## 6. Subagent 协同规划

对照三维效益模型（任务复杂度、上下文关联度、经济与时间效益）评估交付段委托需求：

| 阶段 | 上下文依赖 | 并行收益 | 执行主体 | 决策理由 |
|------|-----------|---------|----------|----------|
| Phase 1：骨架与基建 | 强（决定全局分层与 ffmpeg 契约） | 无（主干基石） | 主线（交付会话） | 结构影响全局，隔离会话缺失上下文易走样 |
| Phase 2：核心管线 | 强（依赖 Phase 1 契约与参数模型） | 无（核心业务链路） | 主线（交付会话） | 认证式状态流转密集，主线直接推演更高效 |
| Phase 3：Fluent 界面 | 中（依赖已定型的后端 API 契约） | 中（可与 Phase 2 尾段并行） | 主线（交付会话） | 与后端共用类型契约，隔离会话需重复装载上下文 |
| Phase 4：打包与验证 | 低（前序产物已定型） | 低 | 主线（交付会话） | 依赖 Windows CI，链路短，无需拆解 |

> **协同结论**：Main-hybrid 已将整个交付段委托给单一 executor 会话，executor 约定为单层执行、不再派发子 agent；本阶段不产生额外委托。前端（Phase 3）与后端（Phase 2）虽具并行理论收益，但受单层约束与共享类型契约影响，改为顺序推进。
